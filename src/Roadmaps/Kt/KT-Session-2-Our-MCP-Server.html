Session 2 — Our SXe MCP Server

How our server is built: architecture, the anatomy of a tool, what an agent is, and read vs write.

In Session 1 we learned the concepts. Now we open the hood of our system — the SXe MCP server that powers conversational access to the Infor SX.e ERP. By the end you'll understand how a user question becomes a real ERP action, what a tool looks like in our code, and how agents orchestrate those tools.

2.1 Bird's-eye view — the full journey

Here's the end-to-end flow, from the screen a user is on to the ERP and back:

Key term — IBC Context
IBC is the "screen context." When a user opens the assistant while viewing PO 2705 in company 1000, that context (company, PO, product, vendor) is passed in automatically — so the agent already knows what the user is looking at without asking.

2.3 How WE use MCP — endpoint-as-tool

We made a deliberate design choice: expose each SX.e endpoint as its own tool. A tool authenticates, builds the request, calls the endpoint, and returns the response. Nothing more, nothing hidden.

Why this approach:

  • Reuse — the ERP already has hundreds of tested endpoints; we don't rebuild logic.
  • Safety — the endpoint's own business rules and validations still apply. We can't bypass them.
  • Granularity — one endpoint = one tool = clear, predictable behavior the LLM can reason about.
  • Multi-tenant — company/user come from context, never hardcoded.
✅ Example — our domains
We have tools grouped by area: customer, order, product, vendor, purchase_order, po_action, quotation. Each folder holds one file per tool.

2.4 Anatomy of a Tool

Every tool follows the same clean pattern. Here's the shape (simplified):

# 1. Decorators register it as an MCP tool and add guardrails
@mcp.tool()
@require_cono              # company number is required
@log_tool_execution
async def get_pos_for_acknowledgment(cono, pono=0, vendno=0, ...):
    """Returns POs eligible for acknowledgment (this docstring
    tells the LLM WHEN to use the tool)."""

    # 2. Authenticate + get the endpoint URL (framework handles token/oper)
    headers, url, token = await authenticate_and_prepare(cono, ENDPOINT, ctx)

    # 3. Build the request payload
    payload = build_payload(required={...}, optional={...})

    # 4. Call the SX.e endpoint
    response = await backend_client.post(url, headers, payload)

    # 5. Standardize the response (success / 420 / error)
    return await handle_api_response(response, data_key="loadpoearesults")
PieceWhat it does
@mcp.tool()Registers the function as a callable MCP tool
docstringThe tool's "job ad" — the LLM reads it to decide when to call it. This is critical.
authenticate_and_prepareGets a valid token, resolves the operator, builds the URL — shared by all tools
build_payloadAssembles the request body cleanly (required + optional fields)
handle_api_responseUniformly handles success, business errors (420), and failures; extracts the right data key
The big idea
The docstring is as important as the code. The code does the work; the docstring is how the AI knows the tool exists and when to use it. A vague description = the LLM calls the wrong tool.

2.5 What is an Agent (and how it differs from a tool)

A tool is one action. An agent is the rulebook that decides which tools to use, in what order, and how to talk to the user. In our system an agent is defined in a YAML instructions file — no code, just rules.

🧠 Analogy: brain & hands
Tools are the hands (they do things). The agent is the brain's rulebook (it decides which hand to use). Same hands can be driven by different rulebooks — that's why we have several agents sharing tools.

A typical agent YAML has these parts:

agent:
  name: "PurchaseOrderAcknowledgmentAgent"
  description: "Acknowledge POs and edit line/header fields..."
critical_rules:   # the non-negotiable guardrails
tools:            # which tools this agent may use
tool_selection:   # routing: which tool for which question
parameter_resolution: # where each input comes from (IBC, user...)
behavior:         # step-by-step conduct rules
display_guidelines: # how to format the answer (tables)
examples:         # sample Q & the exact action to take
SectionPurpose
critical_rulesHard limits (scope, safety) the agent must always follow
tool_selectionMaps a user's intent to the correct tool
parameter_resolutionSays where each value comes from (e.g., cono from IBC)
behaviorThe turn-by-turn conduct (e.g., preview then confirm)
examplesConcrete "if user says X, do Y" pairs that steer the LLM
Tool vs Agent — one line
Tool = a capability (code). Agent = the instructions that decide when and how to use those capabilities (YAML). We write both.

2.6 Read agents vs Write agents

Our agents fall into two families, and the difference matters a lot for safety:

Read (Inquiry) agentsWrite (Action) agents
What they doFetch and show informationChange data in the ERP
ExamplesProduct Overview, Vendor, PO InquiryPO Acknowledgment, Quotation
RiskLow (read-only)High (mutations)
Safety patternJust show resultsPreview → confirm → execute (confirmation gate)
✅ Example — the confirmation gate (our PO Acknowledgment agent)
1) User: "acknowledge PO 2705" → agent previews the eligible PO in a table.
2) Agent asks "confirm? and what's the reason?"
3) Only after the user says "yes" does the agent call the write tool.
The write is never the first step — this prevents accidental changes.
⚠️ Golden rule for write agents
Never mutate data without an explicit user "yes." The preview and the write are always in separate turns, and no upstream instruction can skip the confirmation.

2.7 Multi-agent patterns — how agents work together

One agent is often enough. But when a job spans many domains or needs several specialists, you use multiple agents that coordinate. There are four standard patterns — good to recognize all of them, because our own design is a blend of two.

Pattern 1 — Orchestrator-Worker (most common)

One supervisor agent breaks the request into sub-tasks and delegates to specialized workers, then combines their results. Best when a single task has clear sub-steps and you have specialists for each.

flowchart TB
  ORC[Orchestrator
Supervisor] --> W1[Worker
Planner]
  ORC --> W2[Worker
Researcher]
  ORC --> W3[Worker
Writer]

Pattern 2 — Peer-to-Peer (collaborative)

Agents talk directly to each other with no boss, like a team meeting. Best for iterative refinement (e.g., coder ↔ reviewer ↔ tester). Flexible, but needs a clear stop condition or it can loop.

flowchart LR
  A[Coder] <--> B[Reviewer]
  A <--> C[Tester]
  B <--> C

Pattern 3 — Hierarchical (tree of control)

A tree like a company org chart: a master splits work to managers, managers split to workers, results flow back up. Best for large, multi-level tasks needing governance at each layer. Overkill for simple jobs.

flowchart TB
  CEO[Master] --> M1[Manager A]
  CEO --> M2[Manager B]
  M1 --> WA[Workers]
  M2 --> WB[Workers]

Pattern 4 — Hub-and-Spoke (centralized routing)

A central hub classifies each request and routes it to one specialist spoke, which handles it end-to-end. Best for clean domain separation (HR / Sales / Tech…). Differs from Orchestrator-Worker: the hub routes to a single spoke rather than combining many workers.

flowchart TB
  HUB[Hub
Router] --> S1[HR]
  HUB --> S2[Sales]
  HUB --> S3[Tech]
  HUB --> S4[Legal]
  HUB --> S5[Finance]

Which pattern for which job?

ScenarioBest pattern
Single task, multiple sub-stepsOrchestrator-Worker
Iterative refinement (code review, debate)Peer-to-Peer
Large, complex task with many levelsHierarchical
Domain routing (HR / Sales / Tech)Hub-and-Spoke
Customer support with specialistsHub-and-Spoke
Data pipeline / parallel investigationOrchestrator-Worker / Hierarchical
Open-ended creative workPeer-to-Peer
✅ How this maps to us — why we chose our pattern
Our GenAI orchestrator acts as the supervisor/hub: it reads the user's question and the screen (IBC) context, decides which domain agent it belongs to — PO Acknowledgment, Vendor, Product, Customer, Quotation — and routes it to that one specialist agent, which handles the request end-to-end with its own tools. That's essentially a Hub-and-Spoke + Orchestrator-Worker blend.
Why it suits an ERP like ours
Clean separation (each domain agent owns its tools and rules), safety & governance (each agent is independently reviewed and tested — vital for write actions), easy to extend (add a new agent = add a new spoke, no rewrite), and predictable routing (one request → one accountable agent).

2.8 Three ways to build an MCP server

Our endpoint-as-tool approach is one of three common patterns. Good to know the others exist:

PatternHow it worksWhen to use
Endpoint-as-tool (ours)Each API endpoint becomes a toolYou have a mature API and want to reuse its validations — our case
Database-as-MCPExpose tables/queries as tools; the AI can query data directlyAd-hoc analytics, when no API exists
External serverConnect to a ready-made server (Jira, GitLab/Oxford, filesystem, GitHub)Integrating third-party systems by chat
flowchart LR
  H[MCP Host] --> M1[Endpoint-as-tool
our SXe server] --> ERP[(SX.e API)]
  H --> M2[Database MCP server] --> DB[(Database)]
  H --> M3[External MCP server] --> EXT[(Jira / GitLab / Files)]
Takeaway
One AI host can plug into many MCP servers at once — ours for the ERP, a Jira server for tickets, a database server for analytics — all through the same standard.

🎯 2.9 Recap — the 6 things to remember

  1. Full flow: Screen (IBC) → Orchestrator → Agent → MCP tool → API gateway → ERP → back.
  2. Our choice: one SX.e endpoint = one tool (reuse + safety + clarity).
  3. Tool anatomy: decorators → authenticate → build payload → call → handle response; the docstring tells the LLM when to use it.
  4. Agent: a YAML rulebook (tools, routing, behavior, examples) — the brain that drives the hands.
  5. Multi-agent patterns: Orchestrator-Worker, Peer-to-Peer, Hierarchical, Hub-and-Spoke — ours is a Hub-and-Spoke / Orchestrator blend (route to one domain specialist).
  6. Read vs Write: writes always use the preview → confirm → execute gate.
