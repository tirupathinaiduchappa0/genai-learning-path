Session 1 — Foundations

What is MCP, why it exists, and the vocabulary you need before we open any code.

Goal of this session: by the end, anyone — even with zero AI background — should understand what MCP is, what tools and agents are, and why the whole industry started using this. We build the vocabulary here so Sessions 2 and 3 make complete sense.

1.1 The problem before MCP

AI assistants are only useful if they can reach real data and systems — your ERP, your database, Jira, files, and so on. Before MCP, every AI app had to be connected to every data source with its own custom, hand-written glue code. If you had 4 AI apps and 5 data sources, you needed up to 4 × 5 = 20 separate integrations. Add one new tool and you rewrite it everywhere.

🔌 Analogy: chargers before USB-C
Remember when every phone, camera, and laptop had a different charger? Travelling meant a bag full of cables. USB-C fixed that with one standard plug. MCP is the "USB-C moment" for AI — one standard way to plug any AI app into any tool or data source. 
flowchart LR
  subgraph Before["❌ Before MCP — N × M custom integrations"]
    A1[AI App 1]---S1[(ERP)]
    A1---S2[(Database)]
    A2[AI App 2]---S1
    A2---S3[(Jira)]
    A3[AI App 3]---S2
    A3---S3
  end

This "N×M" explosion is expensive, slow, and breaks constantly. MCP replaces it with a single standard.

With MCP, each data source is wrapped once in an MCP server, and every AI app talks to it through the same standard protocol. The tangled N × M web becomes a clean N + M: add a new app and it instantly works with every existing server; add a new server and every app can use it — no custom glue, nothing to rewrite. 

flowchart LR
  subgraph After["✅ After MCP — one standard protocol (N + M)"]
    B1[AI App 1]--- MCP{{MCP Protocol}}
    B2[AI App 2]--- MCP
    B3[AI App 3]--- MCP
    MCP --- T1[(ERP)]
    MCP --- T2[(Database)]
    MCP --- T3[(Jira)]
  end
✅ The payoff
Before: 3 apps × 3 sources = up to 9 custom integrations. After: 3 + 3 = 6 standard connections — and the gap widens fast as you add more. Build a tool once, every app reuses it.

1.2 LLMs & Agents — a quick primer

An LLM (Large Language Model) — like GPT or Claude — is an AI trained on huge amounts of text. It's brilliant at understanding language and generating answers. But on its own it has two limits:

  • It only knows what it was trained on — it has no live access to your PO #2705 or today's stock.
  • It can only produce text — it can't, by itself, fetch data or change anything.
Key term — Agent
An agent is an LLM given a set of tools plus instructions. Now it can decide, "to answer this, I should call this tool," fetch the real data, and respond. The LLM is the brain; tools are its hands; the instructions are its rulebook.
✅ Example
Ask a plain LLM "What's the status of PO 2705?" → it can only say "I don't have access to that." Ask an agent with a PO tool → it calls the tool, gets "Printed", and answers correctly.

1.3 What is MCP

MCP = Model Context Protocol. It's an open standard (introduced by Anthropic in late 2024, now adopted broadly) that defines a common way for AI apps to discover and use tools and data. Instead of custom glue per app, everyone speaks the same protocol.

Plain-English definition
MCP is a universal language + plug that lets any AI application talk to any set of tools or data sources, without custom integration each time.

Why it's trending:

  • Write once, reuse everywhere — build a tool once; any MCP-compatible AI app can use it.
  • Standard = less breakage — no bespoke code to maintain per app.
  • AI-native — designed specifically for how LLMs/agents discover and call capabilities.
  • Ecosystem — ChatGPT, Claude, IDEs, and enterprise platforms all support it.

1.4 The building blocks: Host, Client, Server

MCP has three roles. Keep the restaurant analogy in mind:

🍽️ Analogy: a restaurant
Host = the dining room where you (the customer) sit and talk. Client = the waiter who carries your order back and forth in a language the kitchen understands. Server = the kitchen that actually prepares the dish (does the real work).
RoleWhat it isExamples
HostThe AI app the user talks toChatGPT, Claude Desktop, our GenAI platform, an IDE
ClientThe connector inside the host that speaks MCP to a serverThe MCP client library embedded in the host
ServerExposes tools/data over MCP and does the workOur SXe MCP server, a GitHub server, a filesystem server

One host can connect to many servers at once (an ERP server, a Jira server, a files server) — all through the same standard.

1.5 Tools, Resources & Prompts

An MCP server can expose three kinds of things. In our work we focus almost entirely on tools.

CapabilityWhat it isEveryday example
Tool ⭐An action the AI can call — a function that does something and returns a result"get PO details", "acknowledge PO", "search products"
ResourceA piece of data the AI can read (like a file or record)a document, a config file
PromptA reusable prompt template the server offers"summarize this order" template
What makes a good tool
Every tool has: a name, a clear description (this is how the LLM decides when to use it), its inputs (parameters), and its output. The description is basically the tool's "job ad" — the LLM reads it to know when to call it.
✅ Example — one of our tools
get_pos_for_acknowledgment — description: "list POs eligible for acknowledgment"; input: company + filters; output: a list of POs. The LLM reads that description and calls it when a user asks "which POs can I acknowledge?"

1.6 A tool call, step by step

Here's what actually happens when a user asks a question that needs live data:

sequenceDiagram
  participant U as User
  participant H as Host + LLM
  participant C as MCP Client
  participant S as MCP Server
  participant API as ERP API
  U->>H: "What POs can I acknowledge?"
  H->>H: LLM reads tool descriptions, picks the right tool
  H->>C: call get_pos_for_acknowledgment
  C->>S: MCP request
  S->>API: call poearetrieve endpoint
  API-->>S: list of eligible POs
  S-->>C: tool result
  C-->>H: result
  H-->>U: "You have 3 POs to acknowledge: ..."

The user never sees any of the middle steps — they just ask a question and get a real answer.

1.7 MCP vs "Connectors" and other buzzwords

You'll hear many terms. Here's how they relate:

TermWhat it meansRelation to MCP
ConnectorA ready-made link between an AI app and a serviceMany connectors are now built on MCP under the hood
Plugin / Custom GPTOlder ways to extend ChatGPT with actionsPredecessors; MCP is the newer open standard
Function callingThe LLM's ability to output "call this function"The underlying mechanism; MCP standardizes how those functions are served
MCP serverA standard program exposing tools/dataThe thing we build
Simple way to say it
"Function calling" is the LLM raising its hand to use a tool. "MCP" is the standard way those tools are offered and connected. "Connectors" are pre-packaged MCP links you can just switch on.

1.8 Real-world: Amazon's "Ask Rufus" (and how WE mirror it)

Amazon's shopping assistant "Ask Rufus" lets you ask questions like "is this jacket waterproof?" or "where's my order?" and it answers by calling APIs behind the scenes — you never navigate to a product spec page or an orders screen. The assistant does the fetching for you.

🛒 The parallel to our work
Our ERP agents work the same way. Instead of a buyer navigating POEA/POET screens, they ask "acknowledge PO 2705" and the agent calls the ERP endpoints (through the API gateway) and returns the answer or performs the action. Ask Rufus for e-commerce ≈ our agents for the ERP.

How other organizations use MCP:

  • Developer tools — IDEs use MCP servers to read code, run tests, query docs.
  • Data/BI assistants — "how many orders last week?" answered by a database MCP server.
  • Ops & ticketing — Jira/ServiceNow MCP servers to create or update tickets by chat.
  • Enterprise ERP (us) — conversational inquiry and actions over SX.e.

🎯 1.9 Recap — the 5 things to remember

  1. Problem MCP solves: replaces messy N×M custom integrations with one standard ("USB-C for AI").
  2. LLM vs Agent: an LLM only talks; an agent (LLM + tools + instructions) can act.
  3. Host / Client / Server: dining room / waiter / kitchen.
  4. Tool: one action the AI can call; its description tells the LLM when to use it.
  5. Real world: Amazon "Ask Rufus" answers by calling APIs — exactly what our ERP agents do.
