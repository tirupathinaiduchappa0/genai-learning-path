The real day-to-day: from a sprint ticket to a shipped tool & agent — plus token optimization and RAG.

Now we go hands-on. This session mirrors what the team actually does every sprint: take a ticket, understand the endpoints, build a tool, test it, write the agent, and ship it. We finish with two advanced topics — a token-optimization experiment and an intro to RAG.

Analyze: read the Jira, find the SX.e endpoints, learn the request payload & response shape (often from the existing UI/frontend code).
Build: add the endpoint constant, then write the tool following our standard pattern.
Test: run the tool in the MCP Inspector with real inputs; verify the response and that it reflects in the ERP.
Agent: write/extend the YAML instructions — tools, routing, behavior, examples.
Review & commit: diagnostics, import check, code review, then commit only the relevant files.
QA: hand off with test questions; QA validates against a tenant.

3.3 Writing agent instructions

We build agent YAMLs part by part (agent → rules → tools → routing → behavior → display → examples), validating the YAML after each part. For a write agent the most important part is the confirmation gate. 

critical_rules: >
  RULE 1 - CONFIRMATION GATE: never call a write tool until the user
  explicitly confirms. Flow is always: preview -> ask -> user says yes -> write.
  RULE 2 - ONE TOOL PER TURN. Preview + write in one turn is forbidden.
  RULE 3 - never bypass API validations; surface errors as-is.
⚠️ A YAML gotcha we hit repeatedly
In a YAML list item, a colon followed by a space (text: more) makes the parser think it's a key/value map and breaks the file. Fix: reword or use a dash (text - more). We validate the whole YAML after every edit to catch this early.

3.4 Best practices & real pitfalls

TopicLesson learned
Full vs sparse payloadSome endpoints need the complete field set (e.g., poearetrieve returned 420 until we sent all fields). Others recalculate if you send a partial record.
Correct data keyExtract the right response array (e.g., loadpoearesults). Wrong key = empty results.
Retrieve-merge-saveTo change a field on a record, retrieve the full record, merge your change, then save — so you don't blank out other fields (this is why PO line price recalculated to 0 when sent sparse).
Stage validationOnly edit/acknowledge POs in eligible stages; reject others with a clear reason.
Write safetyAtomic sequences (remove lock → retrieve → update) so a record is never left half-edited or locked.
Know your limitsSome things aren't a simple field write (PO line price needs the pricing worksheet) — descope honestly rather than fake success.

3.5 Security & multi-tenancy

Our server talks to a real ERP that many companies use. So two questions matter for every single call: who is asking (authentication) and which company's data are they allowed to see (multi-tenancy).

🏢 Analogy — an office building
Authentication is the badge that proves you're an employee. The company number (cono) is which floor your badge unlocks. You can be a valid employee (authenticated) but still only allowed onto your own floor (your tenant). The building never lets you wander onto another company's floor.

How our framework handles it for us

The good news: individual tools don't re-implement login. A shared helper (authenticate_and_prepare) resolves the token, the operator, and the company context before the tool runs. Each tool just receives a valid cono and makes its call.

  • Token & operator — resolved by the framework from the session, not typed by the user.
  • cono (company number) — comes from the request context (the "IBC" context), so the tool always acts on the right tenant.
  • oper (operator) — used for locks and audit; also resolved, never guessed.
⚠️ Rules we never break
  • Never hardcode cono or oper in a tool — always take them from context.
  • Never build queries by string-gluing user input (no SQL/URL interpolation) — it invites injection and broken calls. Validate and .strip() inputs first.
  • Never bypass the ERP's own validations — surface its errors as-is instead of "forcing" a write.
Why this matters
In a multi-tenant system, one leaked or hardcoded company number could show Company A's orders to Company B. Letting the framework own auth + tenant resolution keeps every tool safe by default.

3.6 Token optimization — a POC

🧪 PROOF OF CONCEPT — this is an experiment, NOT in production yet.

The problem

Many ERP endpoints return huge records — sometimes ~100 fields per row (balances, dates, flags, costs, addresses…). But a user's question usually needs only a handful of them. Every field we hand back to the LLM costs tokens, and tokens cost money and context space.

📊 The rough numbers
A single fat endpoint response can cost roughly 800–2100 tokens per question — even when the answer only needed 3 or 4 fields. Multiply that across every question, every user, every day.
Key term — token
A token is a chunk of text (roughly ¾ of a word) that the LLM reads and bills for. Fewer irrelevant tokens = cheaper, faster, and more room in the context window for what actually matters.

The idea

Instead of dumping all 100 fields, send only the fields relevant to the question. We match the user's question to the right fields using embeddings:

Describe fields: map each cryptic field key to a short natural-language meaning (e.g. arbal → "accounts receivable balance").
Embed & store: convert those descriptions to embeddings once and save them to a pickle file (a cached, ready-to-load index).
Embed the question: at query time, turn the user's question into an embedding too.
Match: compare and keep only the fields whose meaning is closest to the question.
Send small: return just those fields to the LLM instead of the whole record.
Key term — embedding
An embedding turns text into a list of numbers that captures its meaning. Texts with similar meaning land close together, so we can measure "is this field related to this question?" mathematically.

The result

In the POC, trimming to only relevant fields cut the payload dramatically — a big drop in tokens per question while still answering correctly. It's promising, but it's still an experiment: it needs accuracy tuning and guardrails (never drop a field the answer truly needs) before it could go to production.

Status: validated as a concept · needs hardening · NOT shipped.

3.7 Bonus — What is RAG?

An LLM only "knows" what it saw during training, up to a knowledge cut-off date. It doesn't know your company's latest documents, your internal wiki, or anything that happened after training. RAG (Retrieval Augmented Generation) fixes that by letting the model look things up before it answers.

📖 Analogy — open-book exam
A plain LLM answers from memory (closed book). RAG is an open-book exam: before answering, it flips to the right pages of your book (your documents) and answers using what it found. Same student, far better answers on your specific material.
Key term — RAG
Retrieval Augmented Generation: retrieve relevant text from your own documents, then feed it to the LLM alongside the question so the answer is grounded in your data — not just training memory.

How it works

flowchart LR
  D[Your files
docs, PDFs, wiki] --> C[Chunk into
small pieces]
  C --> E[Embed each
chunk]
  E --> V[(Vector
store)]
  Q[User question] --> QE[Embed the
question]
  QE --> S{Find closest
chunks}
  V --> S
  S --> R[Relevant chunks
+ question]
  R --> L[LLM writes a
grounded answer]
Ingest: take your files (docs, PDFs, pages) and split them into small chunks.
Embed: convert each chunk into an embedding and store it in a vector store.
Retrieve: embed the user's question and find the chunks whose meaning is closest.
Augment & generate: hand those chunks + the question to the LLM, which writes an answer grounded in your content.
🔗 Notice the connection
RAG and our token-optimization POC (3.6) rely on the same core trick: embeddings + similarity to pull only what's relevant. One trims fields from a record; the other pulls chunks from documents. Learn embeddings once, and both make sense.
⚠️ RAG vs MCP — don't confuse them
RAG brings knowledge (facts from documents) to the model. MCP brings actions & live data (call an endpoint, acknowledge a PO). They're complementary: an assistant can use RAG to know your policy and MCP to actually do the task.
