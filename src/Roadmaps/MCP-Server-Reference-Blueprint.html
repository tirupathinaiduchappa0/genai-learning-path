1. What is an MCP server

The Model Context Protocol (MCP) is an open standard that lets an AI assistant call external capabilities — called tools — in a structured, discoverable way. An MCP server is the program that exposes those tools. Each tool is a well-described function with a name, typed inputs, and a description that tells the AI when and why to use it.

🔌 Think of it as a translation + safety layer
The backend keeps its existing API, validations, and permissions untouched. The MCP server exposes a curated, well-documented slice of that API as conversational "actions" an AI can safely use — it does not add business logic and does not bypass any rule the backend already enforces.

The MCP server is a stateless intermediary. It never talks to the end user directly and never touches the system of record directly — every call goes through the backend's own gateway, which keeps enforcing that system's rules and permissions.

The server's entire job, in one line
Receive a tool call → authenticate → call the real backend endpoint → return a clean, predictable result.

3. Design philosophy

Thin tools

Each tool wraps exactly one backend endpoint. No business logic in the tool.

Authenticate once

One shared helper resolves identity, tenant & token and builds headers + URL for every tool.

One endpoint = one tool

Small, predictable tools the LLM can reason about. Vague mega-tools cause wrong selection.

Config-driven

Local vs cloud chosen by a factory + config, not scattered if-statements.

Stateless & scalable

No conversation state kept; per-request context only. Scales out with no session affinity.

Multi-tenant by design

Tenant & identity read from the inbound request every call — never hardcoded.

Honest errors

Never fabricates success. Backend rejections are surfaced verbatim, not masked.

Middleware order is deliberate
CORS (reject bad browser requests cheaply) → Inbound Auth (verify the caller; 401 early) → Context Injection (extract tenant/user/token into request-scoped context for tools). Each layer depends on the one before it running first.

5. The critical separation — Tools vs Agents

This is the single most important boundary in the whole system.

🖐️ MCP Server (this codebase)

The hands. Python code: tools, auth, config, backend calls. Decides how to execute an action. Changes when a backend endpoint changes or a new capability is added.

🧠 Agent Instructions (assistant platform)

The rulebook. A YAML/prompt authored outside this server. Decides which tool to call, in what order, with what confirmation. Changes when conversational behavior or safety rules change.

✅ Why the split matters
You can add or change tools without touching agents, and refine agent behavior without redeploying the server. A new team building for a different domain builds the server; the agent instructions are authored separately in whatever assistant platform they use.

7. Authentication & multi-tenancy

Every tool calls one shared helper to get ready-to-use headers + URL. That helper is the whole auth model.

flowchart LR
  T[Tool] --> H[authenticate_and_prepare]
  H --> D{Service type
needs session token?}
  D -->|Yes| S[Session manager
cache or login]
  D -->|No| P[Use passthrough
Authorization only]
  S --> B[Build headers]
  P --> B
  B --> U[Build tenant-scoped URL]
  U --> R[headers + url ready]
Tenant comes from an inbound header — never hardcoded, never from a body field or a previous request.
Identity/operator is derived from an identity header and, for backend sessions, fetched from the backend (never trusted from the caller) to prevent impersonation.
Token — passthrough bearer token preferred; client-credentials only as fallback.
Headers + URL built centrally as base/tenant/endpoint; nothing else interpolated in.
⚠️ Two "authentications" — never conflate them
User login session (human → app/assistant, owned by the platform) is different from the MCP server's backend session (server → gateway, cached with a TTL of ~a couple hours, auto-refreshed). If the backend token expires, the user never notices — the server re-authenticates silently.
Security rules (non-negotiable)
Never hardcode tenant/company/operator · never string-interpolate user input into URLs/queries · mask secrets in every log line · validate inputs at the tool boundary · prefer passthrough tokens for real auditability.

8. The tool pattern (one endpoint = one tool)

Every tool, in every domain, follows the same fixed shape:

Register — the tool decorator makes it MCP-visible.
Guardrail decorators — validation (required scope, positive numbers) + execution logging.
Typed parameters + docstring — the docstring IS the description the LLM reads to decide when to call it.
Validate business rules (e.g., "at least one filter/field required").
Authenticate & prepare — one call returns headers + URL.
Build payload — merge required + non-null optional fields.
Call the backend, then handle the response into a standardized result.
The docstring is a contract, not a comment
A good tool docstring states: one-line summary · when to use · when NOT to use (naming the correct alternative tool) · every argument · the return shape. Weak docstrings cause the LLM to pick the wrong tool.

Reads vs writes

Read / preview tool

Validate → prepare → build payload → call → normalize list/dict. Used before any write so the user can review first.

Write tool (atomic sequence)

Remove stale lock → retrieve full record in edit mode → check eligibility → merge only the requested fields → submit the full record. Never a sparse patch.

⚠️ Business rejection ≠ crash · never fabricate success
Transport/5xx errors are raised. Business rejections (e.g., "not eligible", "locked") are returned verbatim so the assistant can explain them plainly. The tool never claims a change happened when it didn't.

9. Adding a new tool (the recipe)

Add the endpoint constant to centralized constants.
Create the tool file in the domain folder (one tool per file).
Apply decorators; write typed params + a complete docstring.
Call the shared helpers in order (auth → payload → call → handle).
Register it (import in the domain's init; ensure the domain is imported at startup).
Test via the MCP protocol: it appears in tools/list and behaves in tools/call.
✅ Keep tools thin
If two tools look nearly identical except for the endpoint and a few field names, that's a sign the shared utility layer needs a new capability — not a reason to copy-paste.

10. End-to-end production flow

How it all comes together in a live system, from a user's question to a natural-language answer:

sequenceDiagram
  participant User
  participant Assistant as GenAI Assistant
  participant Sup as Supervisor Agent
  participant Sub as Sub-Agent
  participant MCP as MCP Server
  participant GW as Backend Gateway
  User->>Assistant: Logs in, asks a question
  Assistant->>Sup: Forwards the question
  Sup->>Sup: Interprets & refactors intent
  Sup->>Sub: Routes to the right domain sub-agent
  Sub->>Sub: Reads instructions + bound tools
  Sub->>MCP: Calls the chosen tool
  MCP->>MCP: authenticate & prepare
  MCP->>GW: Authenticated backend call
  GW-->>MCP: Result / rejection
  MCP-->>Sub: Standardized result
  Sub-->>User: Natural-language answer
Supervisor agent doesn't call tools — it interprets intent and routes to the correct sub-agent.
Sub-agent has its own instructions + a bound list of tools; it decides which one tool to call.
MCP server authenticates (reusing its cached backend token) and calls the gateway.
Response is normalized and handed back; the sub-agent formats it into the final answer.
Where a new team's responsibility ends
They build & deploy the MCP server + tools. The supervisor/sub-agent orchestration lives in the assistant platform (often a separate team). Tool binding happens on the assistant side — the server just exposes well-documented tools; the same tool can be bound to multiple sub-agents.

12. Best practices & pitfalls

TopicRule learned the hard way
Full vs sparse payloadSome endpoints reject partial bodies — send the full field set the real client sends.
Correct response keyExtract the exact nested result key, or you get "no results".
Retrieve-merge-saveTo change one field, retrieve the full record, merge, save the whole record — sparse patches can blank derived fields.
Eligibility checkValidate the record's actual current state before a write; reject ineligible ones clearly.
Honest errorsSurface the backend's rejection message; never fabricate success, never a generic "something went wrong".
No hardcodingNever hardcode tenant/company/operator; fetch identity from the backend for sessions.
No injectionNever string-interpolate user input into URLs/queries; validate & strip first.
Agent sideOne tool per turn; confirmation gate for writes owned by the stateful layer; paginate large result sets; mask nothing but secrets.
⚠️ The confirmation-gate trap (writes)
A stateless sub-agent can't remember it already asked for confirmation, so it can loop forever. The gate must be owned by whichever layer holds conversation state (the orchestrator/agent) — not enforced inside a single stateless tool call.

13. From-scratch build checklist

Scaffold the structure & pin dependencies.
Build the base layer: constants → config/secrets → discovery+factory → session/auth → backend client → context → shared tool utilities.
Create the MCP server instance & the entry point (middleware, routes, lifespan).
Run locally; confirm /healthcheck and startup logs are clean.
Write the first READ tool; register it; verify via MCP protocol.
Add more tools; add the first WRITE tool with the safe atomic sequence.
Write tests (unit + integration + security).
Containerize → deploy with probes & secrets → wire CI/CD.
Author the first agent in the assistant platform & validate end to end.

🎯 The whole idea in three sentences

An MCP server turns individual backend endpoints into safe, well-described tools, handling authentication and multi-tenancy centrally so each tool stays thin. The assistant platform decides which tool to call for a user's request; the server just executes it honestly against the backend. Build the base layer once, keep tools thin and one-endpoint-each, never fabricate success — and the same pattern scales to any business domain.
